systemd and the journal from the command line

On almost every current distribution PID 1 is systemd. It starts services, restarts them when they die, schedules timers and collects every log line. Two commands, systemctl and journalctl, are your whole interface.

You will be able to

  • Inspect, start, stop, enable and debug units
  • Query the journal by unit, priority, time and pattern
  • Write your own service and timer units, system-wide and per-user

Units and states

A unit is anything systemd manages: .service, .timer, .socket, .mount, .target (a named group, like multi-user.target). Two independent properties confuse everyone at first:

PropertyQuestionChanged by
active / inactive / failedIs it running now?start, stop, restart
enabled / disabledWill it start at boot?enable, disable (just symlinks into a target's .wants/)
$ systemctl status
$ systemctl list-units --type=service
$ systemctl --failed
$ systemctl status sshd
$ systemctl status sensor-logger
$ systemctl is-active sshd; systemctl is-enabled bluetooth
$ systemctl cat sensor-logger  # the unit file, with its path
$ systemctl show -p Restart,MainPID sensor-api
$ systemctl list-timers

status is the first thing to run for any service problem: it shows loaded/enabled state, active state, main PID, the cgroup's processes and the last few log lines in one screen.

Changing things

$ systemctl restart sensor-api  # denied: system units need root
$ sudo systemctl restart sensor-api; systemctl status sensor-api
$ sudo systemctl stop sensor-api; systemctl is-active sensor-api
$ sudo systemctl enable --now sensor-api  # enable for boot AND start now
$ sudo systemctl start sensor-logger  # fails: go and read why
CommandEffect
start / stop / restart / reloadNow. reload asks the service to re-read its config without restarting
enable / disable [--now]At boot. --now also starts or stops
maskMake it impossible to start, even as a dependency
daemon-reloadRe-read unit files after you edit them. Forgetting this is the classic mistake
edit UNITCreate a drop-in override in /etc/systemd/system/UNIT.d/ instead of editing the packaged file
reset-failedClear the failed state and the start-rate limiter

The journal

$ journalctl -u sensor-logger  # one unit
$ journalctl -u sensor-logger -p err  # priority err and worse
$ journalctl -p warning -n 5  # last 5 warnings from anything
$ journalctl -k | tail -4  # kernel messages: dmesg without root
$ journalctl -g 'usb|tty'  # grep the message text
$ journalctl -u sensor-api -o cat | tail -2  # message only, no metadata
$ journalctl -u sshd -r -n 2  # newest first
OptionSelectsOptionSelects

-p erremerg, alert, crit, err, warning, notice, info, debug (0–7): that level and worse-kKernel ring buffer

The debugging loop: systemctl status X, then journalctl -xeu X (explain, jump to end, unit), fix, systemctl restart X. In a second pane keep journalctl -fu X running.

Writing a unit

# /etc/systemd/system/sensor-logger.service
[Unit]
Description=Sensor mesh logger
After=network-online.target          # ordering: start after this
Wants=network-online.target          # dependency: pull it in

[Service]
User=sensor                          # do not run as root
ExecStart=/usr/bin/sensor-logger --config /etc/sensor-logger.conf
Restart=on-failure                   # no | on-failure | always
RestartSec=5
Environment=LOG_LEVEL=info
WorkingDirectory=/var/lib/sensor

[Install]
WantedBy=multi-user.target           # what "enable" hooks it into
  • ExecStart needs an absolute path and is not run by a shell: no pipes, ~ or && unless you write ExecStart=/bin/bash -c '...'. A wrong path fails with status 203/EXEC.
  • The service gets a minimal environment, not your .bashrc. Set what it needs with Environment= or EnvironmentFile=.
  • Do not daemonise or write your own log files: stay in the foreground and print to stdout/stderr, and the journal captures it.
  • Hardening is one line each: ProtectSystem=strict, PrivateTmp=yes, NoNewPrivileges=yes, DeviceAllow=/dev/ttyUSB0 rw. systemd-analyze security UNIT scores a unit.

User units and timers

You have your own systemd instance. Units in ~/.config/systemd/user/ are managed with systemctl --user, need no root, and hook into default.target. They stop at logout unless you run loginctl enable-linger $USER once.

# ~/.config/systemd/user/backup.service        # ~/.config/systemd/user/backup.timer
[Unit]                                          [Unit]
Description=Back up ~/work                      Description=Nightly backup

[Service]                                       [Timer]
Type=oneshot                                    OnCalendar=*-*-* 02:30:00
ExecStart=%h/work/scripts/backup.sh %h/work /mnt/nas     Persistent=true        # catch up after downtime

                                                [Install]
                                                WantedBy=timers.target

$ systemctl --user daemon-reload
$ systemctl --user enable --now backup.timer
$ systemctl --user list-timers
$ systemd-analyze calendar "Mon..Fri 07:30"      # check an expression and see the next trigger
$ journalctl --user -u backup.service

Timers replace cron with logging, dependencies, Persistent= catch-up and RandomizedDelaySec=. OnCalendar accepts hourly, daily, weekly, Mon..Fri 07:30, *:0/15 (every 15 minutes); OnBootSec= and OnUnitActiveSec= give intervals. For a one-off: systemd-run --user --on-active=30m notify-send "tea".

On the bench: a user unit is the clean way to keep a serial logger, MQTT bridge or OpenOCD server running: it restarts on failure, logs to the journal, and with a udev rule adding TAG+="systemd", ENV{SYSTEMD_USER_WANTS}="serial-log.service" it can start when the device is plugged in.

Check yourself

You ran systemctl enable foo and rebooted nothing. Is foo running?

Enabled and active are separate. enable --now does both.

You edited a unit file and restarted the service, but the old settings are still in effect. What did you forget?

systemd caches parsed unit files. It even warns you in status that the file changed on disk.

A unit fails with status=203/EXEC. Most likely cause?

203 comes from systemd itself before your program runs. Check the path is absolute and has the x bit.

Which shows only errors from the previous boot?

-b -1 selects the boot before this one: essential after a crash, when the current boot's log is clean.

Networking from the terminal

Network debugging is walking up the stack with one tool per layer until something says no: link, address, route, name, port, protocol.

You will be able to

  • Read interfaces, addresses, routes and neighbours with ip
  • See what is listening and who is connected with ss
  • Test names, ports and HTTP with dig, nc, curl, and capture packets with tcpdump

The ladder

  1. Link: is the interface up with carrier? ip -br link
  2. Address: do I have an IP in the right subnet? ip -br addr
  3. Route: is there a path, and which interface does it use? ip route get 1.1.1.1
  4. Reachability: does the gateway answer? the target? ping -c 3
  5. Name: does the name resolve to what I think? dig +short name
  6. Port: is anything listening, and can I reach it? ss -tlnp, nc -zv host port
  7. Protocol: does it speak correctly? curl -v, tcpdump
$ ip -br link
$ ip -br addr
$ ip addr show wlan0
$ ip route
$ ip route get 192.168.1.44
$ ip neigh  # the ARP table: IP to MAC on the local segment
$ ping -c 3 192.168.1.1
$ ping -c 2 192.168.1.99  # same subnet, no answer: "Host Unreachable" comes from ARP failing

ip abbreviates everything (ip a, ip r, ip l), -br gives one line per interface, -4/-6 filter by family, -j emits JSON, and -c adds colour. In 192.168.1.57/24 the /24 says the first 24 bits are the network: anything in 192.168.1.0–255 is on-link, everything else goes via the default gateway. ifconfig, route, arp and netstat are the deprecated ancestors.

On the bench: ip neigh after a ping sweep is the quickest way to find the IP a new board just got from DHCP, and the first three bytes of the MAC identify the vendor (24:6f:28 is Espressif).

Sockets

$ ss -tln  # TCP, listening, numeric
$ ss -tulpn  # add UDP and owning processes
$ sudo ss -tulpn  # process names for sockets you do not own need root
$ sudo ss -tlnp | grep ':22 '
$ ss -tn  # established connections

Read the local address column carefully. 0.0.0.0:8080 accepts connections from anywhere; 127.0.0.1:631 only from this machine. "It works locally but not from another host" is very often a service bound to localhost, or a firewall (sudo nft list ruleset).

Names and ports

$ dig +short archlinux.org
$ dig lab.lan
$ getent hosts lab  # the way programs resolve: /etc/hosts first, then DNS
$ nc -zv localhost 8080  # is the port open?
$ nc -zv localhost 8081
$ nc -zv 192.168.1.44 80
$ nmap 192.168.1.44  # what else is listening there?

nc without -z connects stdin and stdout to the socket: type an HTTP request by hand, pipe a file across (nc -l 9000 > out on one side, nc host 9000 < in on the other), or poke at a device's debug port.

Scan only what you own or are authorised to test. Port scanning other people's hosts is hostile at best and illegal in many places. Your own lab, your own devices, and deliberately vulnerable targets are fair game and excellent practice.

Packets

$ tcpdump -ni wlan0  # needs root
$ sudo tcpdump -ni wlan0 -c 6
$ sudo tcpdump -ni wlan0 'tcp port 8080'
$ sudo tcpdump -ni wlan0 udp

-n skips name lookups, -i picks the interface, -c N stops after N packets, -A prints payloads as text, and -w file.pcap saves a capture you can open in Wireshark. The filter language (BPF) reads naturally: host 192.168.1.44 and not port 22, tcp[tcpflags] & tcp-syn != 0.

Security lens: put an IoT device on a network you control and run sudo tcpdump -ni wlan0 host DEVICE_IP -w dev.pcap while it boots. DNS queries reveal its cloud endpoints, plain HTTP reveals firmware update URLs, and an unexpected open port (like 2323 on the camera in this sandbox) is an invitation to look closer with nc.

Check yourself

A service shows as listening on 127.0.0.1:5000. Another machine cannot connect. Why?

Loopback is only reachable from the same host. An SSH -L tunnel is a quick way to reach it without reconfiguring.

ping host works but curl http://host says connection refused. What does that tell you?

"Refused" is an active answer (a TCP RST). A firewall that drops silently would give a timeout instead.

Why curl -f in scripts?

HTTP errors are valid responses as far as the transfer is concerned. -f turns them into exit status 22.

Is it CPU, memory, disk or network?

When a machine is slow, guessing wastes time. A fixed sixty-second checklist tells you which resource is saturated, and then a second tool tells you who is using it.

You will be able to

  • Read load average, top, free, df and du correctly
  • Pull live numbers straight from /proc and /sys
  • Know which specialised tool to reach for next

The first minute

$ uptime  # load averages: 1, 5, 15 minutes
$ nproc

$ du -sh ~/work/* | sort -h
$ sudo dmesg | tail -3  # recent kernel complaints: OOM kills, I/O errors, USB resets
$ journalctl -p err -n 5

Finding where the disk went

$ du -sh ~/work
$ du -h -d 1 ~/work | sort -h  # one level deep
$ du -ah ~/work | sort -h | tail -5  # the largest individual entries
$ find ~/work -type f -size +3k -exec ls -lh {} +

On a real machine: sudo du -xh -d 1 / | sort -h (-x stays on one filesystem), or the interactive ncdu /. If df says full but du cannot find the data, a process is holding a deleted file open: sudo lsof +L1 lists them, and restarting that process frees the space.

/proc and /sys: numbers without tools

$ cat /proc/loadavg
$ grep -E 'MemTotal|MemAvailable|SwapFree' /proc/meminfo
$ awk '/MemAvailable/ {printf "%.1f GiB available\n", $2 / 1048576}' /proc/meminfo
$ grep -m1 'model name' /proc/cpuinfo
$ cat /sys/class/thermal/thermal_zone0/temp  # millidegrees Celsius
$ cat /sys/class/net/wlan0/operstate /sys/class/net/wlan0/address
$ cat /proc/sys/vm/swappiness /proc/sys/net/ipv4/ip_forward  # tunables; sysctl -a lists them all

/proc is the kernel's view of processes and system-wide counters; /sys is the device tree with one value per file. Every monitoring tool reads these files, and on a stripped embedded system with no tools installed, cat still works. Writing to them changes kernel behaviour live: echo 1 | sudo tee /proc/sys/net/ipv4/ip_forward is the same as sysctl -w net.ipv4.ip_forward=1.

On the bench: /sys/class/gpio, /sys/class/leds/*/brightness, /sys/bus/i2c/devices, /sys/class/hwmon/*/temp1_input and /sys/kernel/debug are where a single-board computer exposes its hardware. grep -r . /sys/class/thermal/thermal_zone*/temp prints every file name with its value, a handy trick for any directory of one-value files.

Check yourself

Load average is 6.0 on a 2-core machine, yet CPU is 90% idle. What is going on?

Linux counts tasks in state D in the load average. High load with idle CPU points at storage or a hung network filesystem.

free shows 200 MiB free but 5 GiB available. Should you worry?

Unused RAM is wasted RAM, so the kernel caches files in it. "available" is the number that matters.

time make: real 2m10s, user 0m8s, sys 0m3s. Where did the time go?

real minus (user + sys) is time off-CPU. strace -T would show the slow calls.

Devices, serial ports and udev

You plug in a dev board. Between the click of the USB connector and bytes on your screen there are five places it can go wrong, and the terminal shows you each one. The sandbox has an ESP32 behind a CP2102 bridge waiting on /dev/ttyUSB0.

You will be able to

  • Trace a device from kernel log to /dev node to permissions
  • Write udev rules for stable names and access
  • Configure and use a serial line from the shell, and drive flashing tools

What the kernel saw

$ dmesg | tail  # restricted on this distro
$ sudo dmesg | tail -6
$ journalctl -k -g 'usb|tty'  # the unprivileged route
$ lsusb
$ lsusb -t  # the tree, with the bound driver per interface
$ lsusb -v -d 10c4:ea60
$ ls -l /dev/ttyUSB* /dev/ttyS0
$ cat /sys/bus/usb/devices/1-2/product

Run sudo dmesg -w in one pane and plug the device in: you see enumeration, the vendor:product ID, which driver claimed it and the node name it was given. Nothing in dmesg means a cable (many USB cables are charge-only), a hub, or power. An ID with no driver line means the kernel module is missing.

Permissions, the right way

$ cat /dev/ttyUSB0  # Permission denied
$ ls -l /dev/ttyUSB0  # crw-rw---- root uucp
$ id  # are you in that group?
$ sudo usermod -aG uucp op
$ id

The node belongs to group uucp on Arch-based systems and dialout on Debian, Ubuntu and Fedora. Add yourself once, log out and back in (group membership is read at login), and never run your toolchain with sudo. -aG appends; plain -G would replace all your groups, including the one that lets you sudo.

udev rules

udev is the daemon that creates /dev nodes when the kernel announces hardware. Rules in /etc/udev/rules.d/*.rules match device attributes with == and assign properties with = or +=. Ask udev what you can match on:

$ udevadm info -a /dev/ttyUSB0  # walks up the device tree: attributes at each level
$ udevadm info /dev/ttyUSB0  # the properties udev already set
$ cat /etc/udev/rules.d/50-example.rules

# /etc/udev/rules.d/99-bench.rules   (one rule per line, comma-separated)
# a stable name for the ESP32 dev board, usable by group uucp
SUBSYSTEM=="tty", ATTRS{idVendor}=="10c4", ATTRS{idProduct}=="ea60", SYMLINK+="esp32", MODE="0660", GROUP="uucp"
# two identical bridges? add the serial number
SUBSYSTEM=="tty", ATTRS{idVendor}=="0403", ATTRS{idProduct}=="6001", ATTRS{serial}=="A50285BI", SYMLINK+="target_uart"
# raw USB access for a debug probe without root (matches the usb device, not a tty)
SUBSYSTEM=="usb", ATTR{idVendor}=="0483", ATTR{idProduct}=="3748", MODE="0660", GROUP="uucp", TAG+="uaccess"

$ echo 'SUBSYSTEM=="tty", ATTRS{idVendor}=="10c4", ATTRS{idProduct}=="ea60", SYMLINK+="esp32"' | sudo tee /etc/udev/rules.d/99-esp32.rules
$ sudo udevadm control --reload
$ sudo udevadm trigger
$ ls -l /dev/esp32

Why bother: ttyUSB0 is assigned in plug order. With two adapters, the target console and the flasher swap names depending on which you plugged in first, and one day you flash the wrong board. A symlink keyed on vendor, product and serial number never moves. Debug rules with udevadm test $(udevadm info -q path /dev/ttyUSB0) and watch events with udevadm monitor.

Talking over the line

A tty device has line settings: speed, data bits, parity, stop bits, flow control, and a "cooked" mode that echoes and edits lines, which you do not want when talking to a microcontroller. stty reads and writes them.

$ stty -F /dev/ttyUSB0  # current settings: 9600 baud
$ cat /dev/ttyUSB0  # garbage: the board talks at 115200
$ stty -F /dev/ttyUSB0 115200 raw -echo
$ cat /dev/ttyUSB0
$ picocom -b 115200 /dev/ttyUSB0

Garbage characters almost always mean a baud mismatch; nothing at all means TX/RX swapped, no common ground, or the wrong port. With the line configured, plain shell tools work: cat /dev/ttyUSB0 | tee boot.log captures, echo -ne 'help\r' > /dev/ttyUSB0 sends, and ts (moreutils) timestamps each line.

Voltage first. A USB-UART adapter set to 5 V will damage a 3.3 V or 1.8 V target. Measure the target's TX idle level with a multimeter before connecting RX, connect ground first, and leave VCC unconnected when the board has its own supply.

Capstone: six jobs, no hand-holding

Each mission below is a small real task of the kind that lands on your desk: an incident to triage, a report to produce, files to reorganise. They combine everything from the earlier modules, and none of them needs more than a few lines.

How to approach them

  • Look at the data first: head, wc -l, cut one line apart by hand
  • Build the pipeline one stage at a time, checking the output after each |
  • Preview anything destructive with echo in front before you run it for real

The method

  1. State the question as a sentence. "For each hour, how many requests?" already names the key (hour) and the operation (count).
  2. Find the key in one line. Which separator isolates it? head -1 FILE | cut -d: -f2, or awk '{print $4}'.
  3. Filter early. Drop the lines you do not need with grep or an awk pattern before doing anything expensive.
  4. Normalise, then aggregate. sort | uniq -c, or an awk array when you need sums or more than one key.
  5. Rank and trim. sort -rn | head.
  6. Promote it. When you have run the same line three times, put it in a script with set -euo pipefail and arguments.
$ head -2 logs/access.log
$ head -1 logs/access.log | cut -d: -f2  # the hour
$ head -3 logs/auth.log
$ grep -c . logs/access.log logs/auth.log logs/app.log
$ for f in photos/*.jpeg; do echo mv "$f" "${f%.jpeg}.jpg"; done  # dry run: echo first

Final check

You need the ten largest files under /var, staying on one filesystem. Which is closest?

ls is not recursive and du -s gives one total. find emits size and path, sort ranks, head trims: the standard shape.

A script works when you run it and fails from a systemd timer with "command not found". First suspect?

Use absolute paths or set Environment=PATH=... in the unit.

Which one-liner safely deletes all *.o files below the current directory, including names with spaces?

The first breaks on spaces and on the unquoted glob; the second on spaces. -delete (or -print0 | xargs -0 rm) is safe.

What single habit prevents the largest share of shell bugs?

"$var", "$@", "$(cmd)". Then set -euo pipefail and shellcheck catch most of the rest.
