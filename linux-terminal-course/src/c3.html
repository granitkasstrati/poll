Files, inodes and permissions

"Permission denied" is never random. Every access is a lookup of three numbers against nine bits, and once you can do that lookup in your head you can fix it without chmod 777.

You will be able to

  • Read and set modes in both octal and symbolic form, including setuid, setgid and sticky
  • Explain what read, write and execute mean on a directory
  • Reason about inodes, hard links, symlinks, umask and ownership

The inode

A directory is a table of name → inode number. The inode holds everything else: type, mode bits, owner, group, size, timestamps, link count and the location of the data. The name is not in the inode, so one file can have several names (hard links), and renaming never touches the data.

$ ls -li data/parts.csv
$ stat data/parts.csv
$ stat -c '%i %h %a %U:%G %s %n' data/parts.csv /dev/null /dev/ttyUSB0 ~
$ ln data/parts.csv /tmp/hard; ln -s ~/work/data/parts.csv /tmp/soft
$ ls -li data/parts.csv /tmp/hard /tmp/soft  # same inode twice, link count 2
$ readlink /tmp/soft; readlink -f /bin/sh
$ rm /tmp/hard /tmp/soft
Hard linkSymbolic link
IsAnother directory entry for the same inodeA tiny file whose content is a path
Original deletedData lives until the last name goesDangles
Crosses filesystems / points at directoriesNo / noYes / yes
PermissionsShared: it is the same inodeAlways lrwxrwxrwx; the target's bits apply

A relative symlink target is resolved from the directory containing the link, not from where you ran ln. ln -s ../fw/firmware.bin latest is the usual source of "broken link" confusion.

The nine bits

-rwxr-x---  1 op  wheel  4096 Nov 10 09:12 deploy.sh
│└┬┘└┬┘└┬┘     │   │
│ │  │  │      │   group
│ │  │  other  owner
│ │  group bits
│ user (owner) bits
type: - file  d directory  l symlink  c char device  b block device  s socket  p pipe

The kernel checks in this order and uses the first class that applies: are you the owner? then the user bits decide, and only those. Otherwise, are you in the file's group? then the group bits. Otherwise the other bits. Root bypasses the check (except that executing still needs at least one x bit).

BitOn a fileOn a directory
r (4)Read the contentsList the names in it
w (2)Modify the contentsCreate, rename and delete entries in it
x (1)Execute itTraverse it: reach anything inside by name

Two consequences surprise people. Deleting a file needs write permission on the directory, not on the file: deletion edits the directory. And a directory with x but no r lets you open files whose names you already know while hiding the listing.

$ ls -l perm
$ cat perm/locked.txt  # mode 000, even though you own it
$ chmod u+r perm/locked.txt; cat perm/locked.txt
$ mkdir /tmp/box; echo secret > /tmp/box/file; chmod 311 /tmp/box  # wx only
$ ls /tmp/box  # cannot list
$ cat /tmp/box/file  # but can reach a known name
$ chmod 755 /tmp/box; rm -r /tmp/box

chmod, both dialects

$ chmod 640 perm/secret.key; ls -l perm/secret.key  # octal: set all bits at once
$ chmod u+x,go-rwx perm/run.sh; ls -l perm/run.sh  # symbolic: change some bits
$ chmod a=r perm/run.sh; ls -l perm/run.sh
$ chmod -R u=rwX,go=rX perm; ls -l perm  # capital X: execute only where it makes sense
$ chmod -v 600 perm/secret.key

Octal replaces everything; symbolic edits. The capital X sets execute on directories (and files that are already executable) but not on plain files, which makes chmod -R safe. Common modes: 644 files, 755 directories and programs, 600 private keys, 700 ~/.ssh.

Security lens: every setuid-root binary is attack surface: a bug in it is a root shell. On an unfamiliar or embedded system, find / -perm -4000 -type f 2>/dev/null is one of the first things an attacker and an auditor both run, along with find / -writable -type f for files they can modify and find / -perm -2 -type d for world-writable directories.

Ownership and umask

New files start from mode 666 and directories from 777, minus the bits in your umask. With the usual 022 you get 644 and 755. Only root can chown a file to another user; an owner may chgrp a file to any group they belong to.

$ umask; umask -S
$ touch /tmp/a; mkdir /tmp/d; stat -c '%a %n' /tmp/a /tmp/d
$ umask 077; touch /tmp/b; stat -c '%a %n' /tmp/b; umask 022
$ id
$ chown root perm/run.sh  # not permitted
$ sudo chown root:wheel perm/run.sh; ls -l perm/run.sh; sudo chown op:op perm/run.sh

When nine bits are not enough there are ACLs (getfacl, setfacl -m u:alice:rw file; a + after the mode in ls -l signals one), file attributes (chattr +i makes a file immutable even for root) and capabilities (getcap; e.g. cap_net_bind_service lets a non-root service bind port 80 without setuid).

Check yourself

A file is -rw-r--r-- root root inside a directory drwxrwxrwx. Can a normal user delete it?

Unlinking edits the directory. This is exactly what the sticky bit on /tmp prevents.

You own a file with mode ----rw-rw- and you are in its group. Can you read it?

The first matching class decides. Owners can always chmod it back, though.

Which mode makes a shared project directory where new files inherit the group?

2000 is setgid; 775 gives the group write access. 1777 is /tmp, 4755 is a setuid program.

With umask 027, a new directory gets mode…

777 with the 027 bits cleared: rwx r-x ---.

Processes, signals and job control

Everything running is a process with a parent, an owner, a state and a table of open files. The terminal gives you a small set of tools to inspect all of that and to interrupt, pause, resume and end it.

You will be able to

  • Find any process and read its state from ps and /proc
  • Choose the right signal, and know what kill -9 costs
  • Juggle foreground and background jobs, and keep work alive after logout

$ pgrep -a sshd  # PIDs and command lines by name
$ pgrep -u op -a

A zombie uses no memory or CPU, only a process-table slot; you cannot kill it because it is already dead. Fix or kill its parent. An orphan (parent died first) is adopted by PID 1.

/proc: the kernel's view, as files

$ cat /proc/$$/status
$ tr '\0' ' ' < /proc/2350/cmdline; echo  # arguments are NUL-separated
$ grep -E 'State|SigIgn' /proc/2350/status
$ cat /proc/loadavg /proc/uptime
$ grep -c ^processor /proc/cpuinfo

On a real system /proc/PID/ also has cwd and exe (symlinks to the working directory and binary), fd/ (one symlink per open file descriptor), environ, maps (memory layout) and limits. ls -l /proc/PID/fd answers "what is this process writing to?" and even lets you recover a deleted file that is still open: cp /proc/PID/fd/3 rescued.

The escalation ladder: kill PID (TERM), wait a few seconds, then kill -9. KILL leaves temp files, lock files, half-written output and, with a flasher or a database, possibly corrupt state behind. It is the right tool only when TERM has been ignored.

$ kill -l
$ pgrep -a stuck_flash
$ kill 2350; sleep 1; pgrep -a stuck_flash  # still there: it ignores TERM
$ strace -p 2350  # what is it doing?
$ kill -STOP 2350; ps -o pid,stat,cmd -p 2350  # frozen: T
$ kill -CONT 2350; ps -o pid,stat,cmd -p 2350
$ sudo kill 733; pgrep -a sensor-api  # a supervised service comes straight back

That last line is a lesson in itself: a service managed by systemd with Restart=always is resurrected when you kill it. Stop it through its supervisor (systemctl stop), not with signals.

Check yourself

Why try kill PID before kill -9 PID?

SIGKILL never reaches the process: the kernel just removes it.

ps shows a process in state Z. What do you do?

A zombie is already dead. Only its parent reaping it, or the parent exiting, clears the entry.

You closed the SSH window and your long compile died. Which would have kept it alive?

A background job still receives SIGHUP when its terminal goes away, unless it was detached.

A program hangs. strace -p shows the same read(3, ...) blocking forever. What does fd 3 refer to?

0, 1 and 2 are the standard streams. Higher numbers are files, sockets or devices the program opened; the symlink in /proc/PID/fd names it.

Shell scripts that survive contact with reality

Writing a script that works on your example is easy. This module is about the other inputs: file names with spaces, missing arguments, commands that fail halfway, and Ctrl-C at the worst moment.

You will be able to

  • Start every script from a strict, predictable baseline
  • Use conditionals, loops, functions, case and getopts idiomatically
  • Handle errors, clean up with trap, and avoid the classic traps

The skeleton

#!/usr/bin/env bash
set -euo pipefail

usage() { echo "usage: ${0##*/} [-n] SRC DEST" >&2; exit 2; }
die()   { echo "${0##*/}: $*" >&2; exit 1; }

main() {
    [[ $# -eq 2 ]] || usage
    local src=$1 dest=$2
    [[ -d $src ]] || die "no such directory: $src"
    ...
}
main "$@"
LineWhy
#!/usr/bin/env bashThe kernel reads this to pick the interpreter. env finds bash wherever it is installed. Use #!/bin/sh only if you stick to POSIX syntax
set -eExit when a command fails, instead of ploughing on
set -uUsing an unset variable is an error. Catches typos such as rm -rf "$DIRR/"
set -o pipefailA pipeline fails if any stage fails, not just the last
Errors to stderr, exit 2 for usageKeeps stdout clean for pipelines; callers can tell misuse from failure
main "$@"The whole file is parsed before anything runs, and local works
$ cat scripts/backup.sh
$ scripts/backup.sh
$ scripts/backup.sh -n src /tmp/bk
$ bash -x scripts/backup.sh -n src /tmp/bk  # trace every command
$ bash -n scripts/backup.sh && echo "syntax ok"
$ bash -c 'set -u; echo "$nope"'; echo "status $?"
$ bash -c 'set -e; false; echo "never printed"'; echo "status $?"
set -e has exceptions. A failing command does not exit the script when it is part of an if/while condition, on the left of && or ||, or negated with !. And local x=$(cmd) hides cmd's failure behind local's success: declare first, assign second. Treat -e as a safety net and still check the commands that matter.

Loops

$ for f in fw/builds/*.bin; do echo "$(wc -c < "$f") bytes  ${f##*/}"; done
$ for i in {1..3}; do echo "attempt $i"; done
$ for (( i = 0; i < 3; i++ )); do printf 'reg[%d] = 0x%02x\n' $i $((i * 16)); done
$ while IFS=, read -r ref value pkg qty price; do [[ $ref == ref ]] && continue; (( qty > 3 )) && echo "$ref: $qty x $value"; done < data/parts.csv
$ while IFS=: read -r user _ uid _ _ home shell; do (( uid >= 1000 )) && echo "$user -> $shell"; done < /etc/passwd
$ n=0; until (( n >= 3 )); do n=$((n + 1)); done; echo "n=$n"

while IFS=, read -r a b c; do ...; done < file is how you read a file line by line into fields. -r stops backslash mangling; setting IFS on the same line limits it to that read. Loop over globs for files, "$@" for arguments and "${array[@]}" for lists: never over $(ls) or $(cat file).

Functions, case and getopts

$ log() { printf '%s [%s] %s\n' "$(date +%T)" "$1" "${*:2}" >&2; }; log INFO starting up
$ is_elf() { [[ $(head -c 4 "$1") == $'\x7fELF' ]]; }; is_elf /usr/bin/ls && echo yes
$ kind() { case $1 in *.bin|*.hex) echo firmware ;; *.c|*.h) echo source ;; *) echo unknown ;; esac; }; kind main.c; kind fw.hex; kind x
$ f() { local OPTIND opt v=0; while getopts ':vo:' opt; do case $opt in v) v=1 ;; o) echo "out=$OPTARG" ;; :) echo "-$OPTARG needs a value" ;; *) echo "bad option -$OPTARG" ;; esac; done; shift $((OPTIND - 1)); echo "verbose=$v rest=$*"; }; f -v -o x.log a b; f -o; f -z

A function returns an exit status (return 0/return 1), not a value. To hand back data, print it and capture with $(...). Declare variables local or they leak into the caller. In getopts, a colon after a letter means "takes an argument"; a leading colon switches to silent mode so you report errors yourself.

Cleanup with trap

tmp=$(mktemp -d)                      # never /tmp/myscript.$$: predictable names are a security hole
trap 'rm -rf "$tmp"' EXIT             # runs on normal exit, on error under set -e, and after INT/TERM
trap 'echo "interrupted" >&2; exit 130' INT TERM

An EXIT trap is the shell's finally. Register it immediately after creating the thing that needs cleaning up. Use it for temp files, lock files, restoring terminal settings, killing background helpers, and powering a device back down.

$ cat scripts/flaky
$ rm -f /tmp/flaky.count; scripts/flaky; scripts/flaky; scripts/flaky
$ bash -c 'trap "echo cleanup ran" EXIT; echo working; false; echo done'
$ bash -c 'set -e; trap "echo cleanup ran" EXIT; echo working; false; echo done'

What does set -u protect you from?

Without it, rm -rf "$BUILD_DRI/" happily becomes rm -rf /.

SSH, tmux, rsync and tar

Most serious terminal work happens on a machine that is not in front of you: a server, a Raspberry Pi on the bench, a build box. These four tools make a remote machine feel local and keep your session alive when the link drops.

You will be able to

  • Use key authentication and a client config so that ssh name is all you type
  • Build local, remote and dynamic tunnels and hop through jump hosts
  • Keep persistent sessions in tmux; move data with rsync, scp and tar

Keys

You hold a private key; the server lists your public key in ~/.ssh/authorized_keys. Login proves you have the private half without sending it. Generate one Ed25519 key per machine you type on, protect it with a passphrase, and let ssh-agent remember the passphrase for the session.

$ ssh-keygen -t ed25519 -C "op@bench"
$ ls -l ~/.ssh
$ cat ~/.ssh/id_ed25519.pub
$ ssh-copy-id lab  # appends the .pub to authorized_keys on lab
$ ssh-add -l

SSH refuses keys and directories that are too open: ~/.ssh must be 700, private keys 600, authorized_keys 600, and your home directory not group-writable. When key login silently falls back to a password, permissions on the server side are the usual cause; ssh -v host shows each key being offered and rejected.

The client config

# ~/.ssh/config
Host lab
    HostName 192.168.1.20
    User op
    Port 2222

Host pi
    HostName 10.0.0.12
    User pi
    IdentityFile ~/.ssh/id_ed25519
    ProxyJump lab                 # reach pi through lab

Host *.lan
    ForwardAgent no

Host *
    ServerAliveInterval 30        # keep NAT mappings alive
    ControlMaster auto            # reuse one TCP connection...
    ControlPath ~/.ssh/cm-%r@%h:%p
    ControlPersist 10m            # ...for 10 minutes after the last session

For each option the first matching value wins, so specific hosts go first and Host * defaults last. Every tool built on ssh (scp, rsync, git, sftp, VS Code remote) uses these aliases. ssh -G host prints the settings that would actually apply.

$ cat ~/.ssh/config
$ ssh -G lab | head -4
$ ssh lab
$ ssh lab 'uptime; df -h /'  # run a command and return
$ ssh -p 2222 op@192.168.1.20 hostname  # the long way

Quoting matters with remote commands: your shell expands the line first, then the remote shell expands it again. ssh host "echo $HOSTNAME" prints your hostname; single quotes send the $ across.

Doubling an operator applies it to the line: dd, yy, cc, >>. Capitals are shortcuts to end of line: D = d$, C = c$. p pastes what you last deleted or yanked, so ddp swaps two lines and xp swaps two characters.
